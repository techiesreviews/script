# DEMO · How to Back Up a WordPress Site

- Channel: a made-up demo channel
- Status: demo script for script.techies.tools; every person, site and number in it is invented.
- Length: about 2.5 minutes spoken (about 400 words).
- Episode question: If my site broke tonight, could I get it back by tomorrow?
- Viewer takeaway: one backup that runs on its own, one copy stored somewhere else, and one test restore.

## 1 · Hook (0:00–0:20)

[ON SCREEN: a website that turns into a blank white page]

A plugin update. A white screen. And a client asking: "Where did the shop go?" If that happened tonight, could you get your site back by tomorrow?

Most of us think we have a backup. Somewhere. Probably. Until the day we need it.

Hi, I'm Sam, and on this demo channel we make websites a little less scary. Today: how to back up a WordPress site, and how to know the backup actually works.

## 2 · What a backup really is (0:20–0:45)

[ON SCREEN: two boxes appear side by side: "Files" and "Database"]

A WordPress site is two things. The files: themes, plugins and everything you uploaded. And the database: your pages, posts, orders and settings.

A backup is a copy of both, from the same moment. Only the files? You get an empty site. Only the database? You get text without pictures.

So that's the first rule. Files and database, together, every time.

[SILENT: Keep this part short. No tool names yet.]

## 3 · Where backups go wrong (0:45–1:10)

[ON SCREEN: a server with a backup folder inside it, then the whole server goes dark]

The most common mistake is keeping the backup on the same server as the site. When the server fails, the backup fails with it.

The second mistake is a backup that stopped running months ago. Nobody noticed, because nothing told them.

And the third one is a backup that was never tested. It looks fine. Until you try to restore it.

[ON SCREEN: three ticks: "somewhere else", "on its own", "tested"]

## 4 · Set it up once (1:10–1:40)

[ON SCREEN: a backup plugin's settings page, with the schedule set to "daily" and the destination set to cloud storage]

Pick one backup tool and give it three settings. A schedule: daily for a shop, weekly for a small brochure site. A destination: cloud storage, not the same server. And how many copies to keep: thirty days is a good start.

If your host already makes backups, great. Keep them. But make your own as well, stored somewhere the host can't lose.

[SILENT: Don't recommend one plugin by name. Show the settings, not the brand.]
[SILENT: Blur the storage account name.]

## 5 · Test the restore (1:40–2:05)

[ON SCREEN: a staging site restoring from yesterday's backup, with a progress bar]

Here's the part almost everyone skips. Once a month, restore a backup to a test copy of your site. Not your live site. A test copy.

Click around. Do the pages load? Are the pictures there? Can you log in?

If yes, you have a backup. If not, you have a file. Now you know, and today it costs you nothing.

## 6 · Make it a habit (2:05–2:20)

[ON SCREEN: a calendar with the first Monday of every month marked "test restore"]

Put two things in your calendar. Every week: check that the last backup ran. Every month: one test restore.

That's ten minutes a week. Compare that with two days of rebuilding a site from memory.

So, three things. A backup that runs on its own. A copy stored somewhere else. And a restore you have actually tested.
